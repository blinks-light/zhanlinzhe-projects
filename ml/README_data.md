# Dataset Documentation

## Source

The dataset is fully synthetic and generated by `ml/data_pipeline.py`. It contains no
private or scraped data. The generator is deterministic (no randomness), so both dataset
versions can be reproduced exactly from the tagged commits.

Schema (`data/emails.csv`):

| Column | Type | Description |
|---|---|---|
| `text` | string | raw email body |
| `is_spam` | 0 / 1 | binary spam label |
| `category` | string | `spam`, `work`, `personal` or `notification` |

Rows with `is_spam = 1` always have `category = spam`; normal rows use one of the three
sub-categories.

## Versions

| Version | Rows | spam | work | personal | notification | Tag | Commit |
|---|---|---|---|---|---|---|---|
| v1 | 100 | 30 | 26 | 22 | 22 | `data-v1` | `DATASET_V1_COMMIT` |
| v2 | 102 | 26 | 28 | 22 | 26 | `data-v2` | `DATASET_V2_COMMIT` |

### What changed from v1 to v2

1. **Removed 4 near-duplicate / low-information spam messages** (an extra lottery mail,
   a casino bonus, a fake government grant and a duplicate "free entry" mail). This
   reduces label noise and redundancy: spam goes from 30 to 26 rows.
2. **Fixed 2 mislabeled notifications.** The monthly invoice and account statement mails
   were labelled `work` in v1; v2 labels them `notification`. The v1 row counts above
   (`work=26`, `notification=22`) reflect those two labels; the true split is 24 / 24.
3. **Added 6 hard negatives.** Legitimate work/notification emails containing promotional
   wording ("free trial", "discount code", "congratulations", "we won the contract") make
   the spam boundary stricter and reduce false positives.

Net result: 102 rows, slightly better class balance and a harder decision boundary.

## DVC setup

The raw CSV is not committed to Git. Only the pointer file `data.dvc` is tracked.

```bash
dvc init
dvc remote add -d myazure azure://dvc
dvc remote modify myazure account_name wut2026

# SAS token is stored only in the local (git-ignored) config
dvc remote modify --local myazure sas_token "<token>"

dvc add data
dvc push
```

On Windows, if DVC reports `[WinError 5] Access is denied` for its shared cache
(`C:\ProgramData\iterative\dvc\Cache` or `%LOCALAPPDATA%\dvc\site-cache`), point
`DVC_SITE_CACHE_DIR` at a writable folder inside the project before running any DVC
command:

```powershell
$env:DVC_SITE_CACHE_DIR = "D:\NewProjects\projects\.dvc-site-cache"
```

The remote is an Azure Blob Storage container:

| Setting | Value |
|---|---|
| remote name | `myazure` |
| account | `wut2026` |
| container | `dvc` |
| URL | `azure://dvc` |

`.dvc/config.local` is listed in `.gitignore` and in `.dvc/.gitignore`, so the SAS token
never reaches GitHub. Verify with:

```bash
git check-ignore -v .dvc/config.local
git ls-files | grep config.local   # must return nothing
```

## Reproducing a dataset version

```bash
# v1
git checkout data-v1
dvc pull
python ml/data_pipeline.py --version v1 --out data/emails.csv

# v2 (current)
git checkout data-v2
dvc pull
python ml/data_pipeline.py --version v2 --out data/emails.csv
```

Both the generator and the DVC pointer are versioned, so `git checkout <tag> && dvc pull`
restores the exact data used by the model trained at that commit.
